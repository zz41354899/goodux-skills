# 可用性測試法則

## 核心價值

可用性測試透過觀察真實使用者的操作行為,揭露設計盲點與可用性問題。有效的測試不只找出問題,更能理解問題成因、影響範圍與優先順序,為設計改善提供明確方向與驗證依據。

## 適用情境

- 原型或產品開發的任何階段
- 發布前驗證設計是否符合使用者需求
- 發現可用性問題時
- 比較不同設計方案時

## 輸入資訊

- 測試目標與核心假設
- 目標使用者輪廓
- 原型、網站或產品版本
- 想驗證的任務流程
- 可用的時間、人力與測試方式

## 預期產出

- 測試計畫與任務腳本
- 觀察紀錄與問題分類
- 定量與定性分析
- 問題優先順序
- 具體改善建議

## 觸發提示

- 使用者提到「可用性測試」、「usability test」、「使用者測試」、「task flow 驗證」
- 任務需要驗證新流程、原型或頁面是否好用
- 任務需要比較兩個版本哪個更容易使用

## 複雜情境觸發提示

- 任務涉及 B2B 平台、後台流程、資料密集操作或多角色協作場景
- 使用者提到 onboarding、審批流程、客服處理、報表分析或跨系統工作流
- 問題包含任務中斷、切換成本高、例外流程多、培訓成本高或不同角色表現差異大
- 團隊需要驗證複雜流程到底是結構問題、內容問題還是權限/狀態設計問題

## 先問哪些澄清問題

- 這次測試要驗證哪一段關鍵流程?成功標準是什麼?
- 有哪些角色需要分開測試?他們的任務和權限是否不同?
- 目前最常出錯、最耗時或最容易放棄的是哪個步驟?
- 測試對象是現有產品、原型還是新概念?保真度夠不夠支撐測試?
- 是否需要測試例外情境,例如退件、逾時、缺資料或跨部門交接?
- 測試結果會如何被使用?是排優先序、說服利害關係人還是決定是否上線?

## 可搭配哪些其他 skill

- `user-interview`: 先了解問題背景或在測試後深挖原因
- `wireframing`: 針對發現快速提出低成本改善方案
- `prototyping`: 建立更完整的可測試互動流程
- `information-architecture`: 若問題來自分類與導航,回頭調整架構

## 複雜需求範例

### B2B 客戶導入流程測試

- 情境: 新客戶管理員需要設定帳號、匯入資料、邀請成員與完成權限配置
- 測試重點: 找出哪一步最耗時、最容易中斷,以及哪些說明不足

### 後台審核工作流測試

- 情境: 審核員需要在有限時間內處理大量案件,主管還要覆核例外案件
- 測試重點: 驗證案件資訊是否足夠、狀態切換是否清楚、批次操作是否容易出錯

### 多角色客服處理流程

- 情境: 客服、技術支援與主管共同使用同一工單系統
- 測試重點: 檢查交接資訊是否完整、不同角色是否能快速找到下一步

## 工作流程

### 1. 定義目標

**明確測試目標**
```markdown
測試目標範例:
- 評估新註冊流程的完成率
- 發現結帳流程中的障礙
- 比較兩種導航設計的效率
- 驗證搜尋功能是否直觀
```

**設定成功指標**
- 任務完成率 (目標: >80%)
- 完成時間 (目標: <3 分鐘)
- 錯誤次數 (目標: <2 次)
- 滿意度評分 (目標: >4/5)

### 2. 準備任務

**設計真實任務**
```markdown
✅ 好的任務:
「你想買一雙運動鞋送給朋友當生日禮物,預算是 2000 元以內。請找到合適的商品並完成購買。」

❌ 不好的任務:
「請點擊導航列的『商品』,然後選擇『運動鞋』分類。」

任務設計原則:
- 給予情境和目標,不要給步驟
- 使用真實的使用情境
- 避免使用介面上的文字
- 每個任務測試一個主要功能
```

**任務清單範例**
```markdown
測試: 電商網站結帳流程

任務 1: 探索性任務
「請花 2 分鐘瀏覽這個網站,告訴我你的第一印象。」

任務 2: 搜尋任務
「你想找一件適合夏天穿的 T 恤,請找找看。」

任務 3: 購買任務
「請將這件 T 恤加入購物車並完成結帳。」
(提供測試用信用卡資訊)

任務 4: 帳戶管理
「請查看你的訂單狀態。」
```

### 3. 招募參與者

**參與者人數**
```markdown
尼爾森研究:
- 5 位使用者可發現 85% 的可用性問題
- 15 位使用者可發現 95% 的問題

建議:
- 定性測試: 5-8 位
- 定量測試: 20+ 位
- 多個使用者群體: 每群 5 位
```

**招募標準**
- 符合目標使用者特徵
- 沒有參與過產品開發
- 願意出聲思考
- 可提供誠實反饋

### 4. 執行測試

**測試流程**
```markdown
1. 歡迎與說明 (5 分鐘)
   - 自我介紹
   - 說明測試目的
   - 強調測試的是產品,不是使用者
   - 取得錄影/錄音同意

2. 背景問題 (5 分鐘)
   - 了解使用者背景
   - 相關經驗
   - 技術能力

3. 執行任務 (30-40 分鐘)
   - 一次給一個任務
   - 鼓勵出聲思考
   - 觀察並記錄
   - 必要時追問

4. 後續訪談 (10 分鐘)
   - 整體印象
   - 困難點
   - 改善建議
   - 滿意度評分

5. 結束與感謝 (5 分鐘)
```

**出聲思考協定**
```markdown
引導語:
「請在使用過程中說出你的想法,例如:
- 你在看什麼
- 你在想什麼
- 你為什麼這樣做
- 你期望會發生什麼」

提醒語:
「請繼續說出你的想法。」
「你現在在想什麼?」
```

**主持人守則**
```markdown
✅ 應該做:
- 保持中立
- 觀察並記錄
- 適時追問
- 給予思考時間

❌ 不應該做:
- 引導使用者
- 幫助使用者
- 為產品辯護
- 打斷使用者
```

### 5. 記錄問題

**觀察記錄表**
```markdown
| 時間 | 任務 | 觀察 | 嚴重程度 | 引言 |
|------|------|------|----------|------|
| 3:25 | 結帳 | 找不到優惠券輸入欄位 | 高 | "我有優惠券但不知道在哪裡用" |
| 5:10 | 搜尋 | 搜尋結果不相關 | 中 | "這些結果跟我要找的不一樣" |
```

**問題分類**
```markdown
嚴重程度:
- 🔴 嚴重: 阻止任務完成
- 🟡 中等: 造成困擾但可完成
- 🟢 輕微: 小問題,不影響使用

問題類型:
- 導航問題
- 標籤不清楚
- 缺少功能
- 錯誤訊息
- 視覺設計
- 效能問題
```

### 6. 分析結果

**定量分析**
```markdown
任務成功率:
- 任務 1: 8/10 (80%)
- 任務 2: 6/10 (60%) ⚠️
- 任務 3: 9/10 (90%)

平均完成時間:
- 任務 1: 2:30
- 任務 2: 4:15 ⚠️
- 任務 3: 3:00

錯誤次數:
- 平均: 2.3 次
- 最多: 5 次 (任務 2)
```

**定性分析**
```markdown
主要發現:
1. 搜尋功能不直觀 (6/10 使用者遇到問題)
2. 結帳流程過長 (平均 4 分鐘)
3. 優惠券輸入位置不明顯 (8/10 找不到)

使用者引言:
"我不確定要在哪裡輸入關鍵字。"
"步驟太多了,我都不知道還要填多久。"
"我有優惠券但找不到在哪裡用。"
```

### 7. 提出建議

**優先順序**
```markdown
P0 - 立即修復:
- 修復搜尋功能
- 在明顯位置加入優惠券欄位

P1 - 下個版本:
- 簡化結帳流程
- 改善錯誤訊息

P2 - 未來考慮:
- 加入進度指示器
- 優化手機版體驗
```

## 最佳實踐

1. **足夠樣本**: 5 位使用者可發現 85% 的可用性問題
2. **出聲思考**: 使用「出聲思考」協定了解使用者想法
3. **保持中立**: 保持中立,不要引導或幫助使用者
4. **真實任務**: 測試真實任務而非功能展示
5. **記錄數據**: 記錄定量數據(完成率、時間)和定性觀察
6. **盡早測試**: 盡早且頻繁地測試
7. **迭代改善**: 根據測試結果快速迭代

## 遠端測試

**工具**
- Zoom / Google Meet (視訊會議)
- UserTesting (專業平台)
- Lookback (錄製工具)
- Maze (原型測試)

**注意事項**
```markdown
✓ 提前測試技術設備
✓ 要求使用者分享螢幕
✓ 準備備用方案
✓ 考慮時區差異
✓ 錄製整個過程
```

## 範例輸出

```markdown
# 可用性測試報告

## 測試概況
- 測試日期: 2024/03/10-12
- 參與者: 8 位
- 測試對象: 電商網站結帳流程原型
- 測試方式: 遠端測試

## 參與者背景
- 年齡: 25-45 歲
- 線上購物頻率: 每月 2+ 次
- 裝置: 手機 (5 位) + 電腦 (3 位)

## 任務結果

### 任務 1: 搜尋商品
- 成功率: 75% (6/8)
- 平均時間: 3:15
- 主要問題: 搜尋按鈕不明顯

### 任務 2: 加入購物車
- 成功率: 100% (8/8)
- 平均時間: 1:30
- 無重大問題

### 任務 3: 完成結帳
- 成功率: 62.5% (5/8)
- 平均時間: 5:20
- 主要問題: 流程過長,缺少進度指示

## 關鍵發現

### 🔴 嚴重問題

**1. 結帳流程過於複雜**
- 影響: 3 位使用者放棄結帳
- 引言: "步驟太多了,我不想繼續了。"
- 建議: 合併為一頁式結帳

**2. 優惠券輸入位置不明顯**
- 影響: 7/8 使用者找不到
- 引言: "我有優惠券但不知道在哪裡輸入。"
- 建議: 在購物車頁面加入明顯的優惠券欄位

### 🟡 中等問題

**3. 缺少進度指示器**
- 影響: 使用者不知道還要填多少資料
- 建議: 加入步驟指示器 (1/3, 2/3, 3/3)

**4. 錯誤訊息不清楚**
- 影響: 使用者不知道如何修正錯誤
- 建議: 提供具體的錯誤說明和解決方法

## 改善建議

### 立即修復 (P0)
1. 重新設計結帳流程為一頁式
2. 在購物車加入優惠券輸入欄位
3. 改善搜尋按鈕的視覺層級

### 下個版本 (P1)
1. 加入結帳進度指示器
2. 優化錯誤訊息
3. 加入自動填寫地址功能

## 滿意度評分
- 整體滿意度: 3.2/5
- 易用性: 2.8/5
- 視覺設計: 4.1/5

## 下一步
- 根據 P0 問題重新設計原型
- 2 週後進行第二輪測試
```
